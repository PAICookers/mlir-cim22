## 运行通用 pytest

准备匹配源码的 USB wheel、Python 3.12 与项目所需的 torch-mlir。按
[平台发现](hardware-recovery.md#平台发现)核对设备。用项目实板套件的 USB 配置示例
作为模板，填入现场的标识、接口、端点和串口。频率或等待覆盖见
[时序配置](timing-tuning.md#配置默认值与覆盖方式)。

在当前版本提供套件和观察器时，从仓库的 `python/` 目录运行。把下面两个 JSON 文件名
替换为现场配置的路径。按 [pytest 观察器](vivado-lab.md#pytest-观察器)准备 ILA 配置。

```sh
python -m pytest tests/test_board_cases.py
python -m pytest tests/board -m "board and not local_board" --run-board --board-config "usb.json" --board-ila-config "ila.json"
```

首条命令是离线检查。实板用例显式启用、单进程执行，并要求 ILA 观察器。
失败后停止其余实板用例。
换档后先跑供应方基线，确认协议、计算及关闭状态，再执行编译器用例。通用覆盖包括
INT8/BF16、Macro/核放置、事务切分、驻留与重开、重复执行及 Host 归约。
记录实际动态 dispatch 和相应数值对照。详细覆盖按
[运行时验证矩阵](runtime-validation.md#覆盖矩阵)核对。

比较稳定性时可单独运行 `tests/board/test_stability.py`。每档使用独立 JSON 和
`--board-output` 路径，按需传入 `--board-repeats 32`。保留首轮，按
[耗时统计方法](timing-tuning.md#实测耗时和模型估算)报告热运行和观测开销。

## 定位当前环境

- 从接手的工作树确认项目根目录、分支、提交、本地差异和适用的 `AGENTS.md`。
  根据当前构建配置、工具输出和文件存在性定位运行时、编译器及测试入口。
  路径和文件名示例只用于搜索。记录本轮实际加载的库和使用的用例版本。
- 按用户提供的位置或当前环境发现供应方包、FPGA 工程、LTX 和 SDK。
  每项可独立位于工作树外。分发技能时保留其 `references/`，项目制品、工具链
  与供应方材料由接收方按实际可用性提供。供应方原件以只读方式使用。
- 运行脚本所需的工作目录、输入路径、工具路径和设备标识均按实际环境解析或显式传入。
  各轮输出使用新目录，记录当前解析出的路径、来源和哈希供复查。
- 缺少原供应方用例时，可用现有或自行构造的输入验证运行时，并按实际参考说明
  覆盖。缺少必需的协议、兼容信息或送达观测时，暂停受影响的实板步骤，
  继续可完成的离线准备。

复用已验证的工具、用例和基线。重新确认设备状态与版本兼容性。按现场证据决定恢复
范围。INT8 与 BF16 共用主要控制流程，编码和参考模型按数据类型选取。

## 1. 固定基准和比较范围

- 从供应方交付的版本清单定位控制程序和输入。按数据版本配对参考输出。
- 固定源码/二进制/实际加载库、数据生产者和哈希；记录 FPGA 编程由谁确认、
  工程/探针来源、已知 FX3 身份、时钟配置和本次恢复范围。未提供的信息记为未知。
  文件哈希记录制品来源，板上状态由现场确认。
- 核对返程目标、路由、Macro/模式、Weight_EXP、Cache/CIM、Once/Idle、等待和
  读取顺序。输入相同或复用原函数不等于最终发送字节相同。
- 确实拥有并移植供应方程序时，平台适配局限于必要行为，列出芯片帧、传输分块、
  节流、接收并发和ILA暂停的实际差异。没有原Windows程序/轨迹，就不声称平台
  对照或RTL周期时序等价；这不阻止已有生产运行时的验证。
- 按任务和原用例选择权重读取。保留读取时分别记录协议和数值。已有缺陷时按验收
  约定单列差异或标记跳过数值比较，使用计算结果判断推理正确性。纯推理无需额外
  读取。请求变化后按实际读回计划重算接收长度。

## 2. 发送前离线核查

优先复用当前项目codec、现有生成/检查组件；拥有供应方纯函数时可对照，原脚本
不在接收方环境中并非必须补齐。不得运行会改写供应方目录的脚本。
检查真实发送计划的包边界、body 长度、地址和字节序；body 高位可能类似请求头，
不能逐个 flit 仅凭高四位推断发生了额外读请求。

采用新程序或改了解析时，运行相关离线检查：合法回包、分片、缺失/重复/错误头、
padding 和数值扰动。离线通过不能代替实际 USB 执行；已有未变检查无需每轮重写。

## 3. 当前硬件和时钟

- 按[平台发现](hardware-recovery.md#平台发现)核对枚举、权限、接口及占用者。
- 按[时序配置](timing-tuning.md#配置默认值与覆盖方式)核对三阶段 PLL 和五项等待。
- 按 [Vivado Lab 步骤](vivado-lab.md#连接并辨认探针)刷新并确认探针。
  FPGA 编程、CIM 复位和 FX3 恢复分别记录。

## 4. 基线、配置和 Work 门禁

1. 用当前板卡可用的ILA或已建立的等效观测确认空闲：输出FIFO无遗留数据、计数稳定，
   翻转握手 req=ack；0/0、1/1 都可能正常。保留新鲜采样，不用旧 CSV 充数。
   没有探针工程时不套用旧采集脚本；所需门禁没有可用观测就暂停对应上板步骤，
   继续离线部分，并说明门禁未验证，不能写成通过。
2. 在实际将执行的同一 USB 句柄上做有界空闲 IN 检查，无意外数据或立即错误。
3. 配置期间保持接收活动，记录实际提交与完成长度。Work 前比较实际成功 TX
   前缀与计划；结合接受计数、FIFO 与握手确认送达。marker 出现本身不是放行条件。
4. 从本轮字节量和实际探针语义推导计数增量；32bit桥常见OUT字节/4，跨轮还须
   加上已完成读回，不复制历史绝对计数。送达计数不证明每个SRAM单元内容。

JTAG 采集由单一所有者串行操作；完成或停止上一采集后才重新 arm。不关闭用户
已有 GUI/server，不改写正在进行的采集，也不把本任务采集扩成重新编程授权。

## 5. 回包和数值

先核对完整长度、type/core/row、源通道、重复/缺失、padding 和尾随数据，再做
数值比较。Macro/dtype 不在当前结果头里，由选宏和请求上下文归属；切换 Macro
前收齐其已请求结果。不要把某次观测到的源通道03写成所有包的硬性前缀。
已验证的32b记录流可覆盖源通道0..7，包内通道保持一致；合法字段范围仍按当前
版本核对。接收路径应及时检查完整包并传播失败，不能把已知结构错误留到整轮
发送后才处理；不为此擅改供应方既定的合法并发或批量请求顺序。

INT8/BF16 解释与参考选择见 [运行时验证](runtime-validation.md#数值参考)。
不能把缺失数据补零比较，不能根据错误 actual 重建 expected。结果文件写入失败
也不能报告可复核的数值通过。

完整且数值不符：保存坐标/位型，定位芯片侧观测→FPGA FIFO→FX3/Host→解码的
最早差异；不为得到匹配而改布局、缩放或 golden。时序扫描可按
[换档条件](timing-tuning.md#失败后能否换档)继续计划内的下一档。只对实际捕获范围作结论。
传输、协议或送达失败时停止新 OUT，按现场证据处理恢复。禁止自动复位、清端点或循环重发。
预期取消、真实错误和重开行为需要区分时，查 [USB 收尾与重开](hardware-recovery.md#usb-收尾与重开)。

## 6. 保存结论

报告本次实际数据、相对供应方流程的改动、TX/RX数量、协议覆盖、数值差异及
清理状态。确认运行时包含相应支持后，可以正常关闭并重开测试，不要求永久保持
句柄或逐例断电。按团队报告约定保存本轮输出、命令和必要哈希。

报告区分供应方程序、编译事务、Host 回放与完整模型入口。按实际执行范围记录覆盖。
历史记录用于对照，本轮结果以新证据为准。技能保留可复用流程，测试数据和结果存入
本轮证据目录。
