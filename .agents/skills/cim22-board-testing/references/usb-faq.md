# USB 注意事项与 FAQ

仅在相关异常或用户提问时读取。Linux 的接口设置修复适用于对应版本和驱动。
Windows 的 CyAPI 状态码、清理和回环诊断见 [Windows 实板与 USB](windows-board.md)。

## 测试结束后能关闭，再重新打开吗？

可以。已验证的Linux修复先GET_INTERFACE，仅在实际setting不符时才SET_INTERFACE。
已有CIM22环境中数据会话后冗余SET_INTERFACE(0,0)曾触发下一IN的EPROTO/0B；条件设置后
已验证多个独立进程正常开、测、关。不是“Linux不能连续测试”，也不要求永久
保持句柄。该触发证据不能解释全部历史超时或外推所有内核/libusb/FX3版本。

接收方先核对实际加载库与当前源码是否包含条件设置，不能因技能描述修复就假定
本地已更新；实现可能名为 `LibusbUsbDriver.cpp`，按当前checkout搜索。复现相似
问题时检查失败步骤，不必重做已定位的致故障操作，也不需要作者的原始记录才能
理解或检查此修复。

## 需要重编译 Cypress Linux 内核驱动吗？

CyUSB Linux 是 libusb 用户态封装，不能把它称为另一套内核驱动。先查可执行文件
实际链接的库。没有SDK包也可检查已安装库；压缩包哈希不同本身不支持更换传输栈。
若比较SDK版本，应比较实际bulk实现和链接关系，而非假定另一成员持有相同包。
SDK、系统libusb、设备固件、FPGA工程分别记录。已取得GUI/手册时再按需使用；
GUI可能claim接口，不与测试并用。不因缺少作者的SDK目录自动安装库或加载固件。

## 超时、status1、取消各说明什么？

- 超时只是该请求未在期限内完成；没有底层证据时不能叫驱动故障。
- libusb transfer status1不自动等于内核EPROTO；若需定位，记录请求是否submit、
  URB完成状态和actual length，并结合FPGA观测。usbmon不是物理总线抓包。
- 成功结果后预期0B取消可以正常；保留合法尾数据、drain及真实错误，再回收请求、
  释放接口。清理失败与此前已完整保存的数值结果分别判定。

## 再次失败怎么办？

停止当前异常范围的新OUT，保存实际前缀和接收/完成记录。先查重新枚举后的权限、
端点/占用、当前库及硬件恢复范围；需要时再设计取消、释放、重开等分段实验。
失败后的链路不能当作另一变量的干净起点。不自动reset、clear-halt、换固件或
循环重试；按具体证据提出恢复需要，避免反复断电代替定位。
